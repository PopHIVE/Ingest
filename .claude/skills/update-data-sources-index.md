# Update the data sources index

`docs/data_sources_index.json` is a lightweight catalog of every standardized
data source in this repo. It is **regenerated by `scripts/build_docs.R`**, which
runs automatically every day and on every `measure_info.json` change.

**The two hand-editable text fields — `summary` (per dataset) and
`dataset_stratification` (per file) — are preserved across rebuilds.**
`build_docs.R` reads the existing `docs/data_sources_index.json` and keeps
whatever is already in those two fields, so **you can edit them directly in the
JSON and they will not be overwritten.** Every other field (`github_link`,
`latest_date`, `bundles`, links) is always recomputed, so editing those is
pointless — fix the source data instead.

Fallbacks for a **brand-new** dataset/file that has no text yet:
- `summary` → a concise extractive summary (first sentence of the source's
  `_sources` description).
- `dataset_stratification` → a value from `resources/stratification_cache.json`
  (keyed `"<dataset>/<filename>"`) if present, otherwise a blurb derived from the
  file name.

So the caches/fallbacks only fill the gap on first appearance; once real text is
in the JSON, that text wins and persists.

## Fields in each dataset entry

`build_docs.R` derives these automatically (no action needed):

| Field | Source |
|-------|--------|
| `dataset` | source folder name under `data/` |
| `name` | first `_sources[].name` in `measure_info.json` |
| `github_folder` | link to the source folder on GitHub |
| `github_link` | direct raw link to the **primary** `standard/*.csv.gz` (prefers `data.csv.gz`) |
| `data_url` | first `_sources[].url` |
| `data_dictionary` | `https://pophive.github.io/Ingest/#<section-id>` |
| `latest_date` | most recent date found across the source's standard files |
| `bundles` | bundles that consume the source (from each `bundle_*/process.json`) |
| `files` | present only when the source has **>1** `standard/*.csv.gz`; one entry per file with `dataset_link` (direct raw link) and `dataset_stratification` |

The two hand-editable fields:

- **`summary`** — one to two plain-English sentences describing the dataset.
- **`dataset_stratification`** (inside each `files` entry) — a short phrase
  describing how that file is stratified **beyond time and geography**.

## Procedure

### 1. Find what needs text

From the repo root, list source folders (everything in `data/` that is not
`bundle_*` and has both a `measure_info.json` and at least one
`standard/*.csv.gz`). Then open the current `docs/data_sources_index.json`:

- A dataset needs a **summary** if its `summary` is missing, empty, or is just
  the extractive fallback (i.e. reads like the raw first sentence of the source
  description rather than a purpose-written 1-2 sentence blurb).
- A multi-file dataset needs **stratification** text if any file's
  `dataset_stratification` is missing or is a filename-derived placeholder
  (e.g. `"Stratified by <tokens>."` or `"Overall; no stratification..."`).

Default when a new dataset is added: only fill what's missing/placeholder; leave
good existing text alone. If the user asks to refresh a dataset, rewrite it.

### 2. Write the summary (1-2 sentences)

Read `data/<dataset>/measure_info.json` and use the `_sources` `description`
field(s) — consider all entries under `_sources`, since multi-source datasets
(e.g. `nchs_mortality`) cover several distinct things. Write **one to two
plain-English sentences** describing what the dataset contains, suitable for a
data catalog: no preamble, no quotes, no markdown.

Put it **directly in `docs/data_sources_index.json`** as that dataset's
`summary` value. It is preserved on rebuild.

### 3. Write stratification blurbs for multi-file datasets

For each dataset with more than one `standard/*.csv.gz`, write a short phrase per
file describing its stratification dimension **other than time and geography**.
Infer it from the file name and, when helpful, the column headers — the
non-`time`/non-`geography`/non-value columns (e.g. `age`, `sex`,
`race_ethnicity`, `serotype`, `vaccine`, `grade`) are exactly the stratification.
Read a file's header with `vroom::vroom(path, n_max = 0)`. Keep each blurb to a
fragment or one short sentence.

Examples:
- `nchs_mortality/data_state_21_causes.csv.gz` → `"Age-adjusted mortality rates for 21 selected causes of death (state-level)."`
- `narms/data_resistance_agent.csv.gz` → `"Human isolate resistance by bacterial genus/serotype and individual antimicrobial agent (with CLSI class)."`
- `yrbss/data_age_sex.csv.gz` → `"Youth risk behaviors by age group and sex."`

Put each blurb **directly in the file's `dataset_stratification`** in
`docs/data_sources_index.json` (preserved on rebuild). For a dataset that has
**no** JSON entry yet, you can instead pre-seed
`resources/stratification_cache.json` (keyed `"<dataset>/<filename>"`) so the
first build picks it up.

### 4. Regenerate the index

From the repo **root** (not `docs/`):

```powershell
Rscript scripts/build_docs.R
```

This rewrites `docs/index.html`, `resources/data_manifest.json`, and
`docs/data_sources_index.json`, keeping the `summary` and
`dataset_stratification` text you wrote and recomputing every other field. No
API key is required.

### 5. Verify

Open `docs/data_sources_index.json` and confirm each affected entry has a
purpose-written `summary`, a `github_link` pointing at a real
`standard/*.csv.gz`, and — for multi-file sources — a `files` array whose entries
each have a `dataset_link` and a meaningful `dataset_stratification`. Report
which datasets were added or refreshed.

## Notes

- The GitHub raw base is `https://raw.githubusercontent.com/PopHIVE/Ingest/main`;
  links look like `.../main/data/<dataset>/standard/<file>.csv.gz`.
- Commit the regenerated `docs/data_sources_index.json` (and
  `resources/stratification_cache.json` if you seeded it) together with the rest
  of `docs/` and `resources/data_manifest.json`.
- One-time reseeding trick: if the JSON holds a placeholder you want a cache
  value to override, delete `docs/data_sources_index.json` before running the
  build so the cache/fallback repopulates it. Summaries have no cache, so only
  do this after the summaries you want are safely in the JSON (or you'll drop
  back to the extractive fallback).
