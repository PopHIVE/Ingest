# create-bundle

Create and build a new bundle: scaffold the `bundle_<name>` directory, write `build.R` to combine standardized source files into `dist/*.parquet`, build it with `dcf`, and write a well-documented `measure_info.json`.

A **bundle** combines one or more already-standardized data **sources** (the `data/<source>/standard/*.csv.gz` files produced by `ingest.R`) into consolidated **parquet** files under `dist/`, for the website/visualization layer. Bundles never download raw data — they only read source `standard/` outputs.

## Usage

```
/create-bundle <bundle_name> [which sources/files to combine and what each output should contain]
```

`bundle_name` must start with `bundle_` (e.g. `bundle_youth_wellbeing`). If the user omits the prefix, add it.

## What this skill produces

```
data/bundle_<name>/
├── build.R              # combines source standard/ files -> dist/*.parquet
├── measure_info.json    # documents every dist column (+ sources + file→parquet map)
├── process.json         # auto-generated by dcf (tracks source_files → parquet map)
└── dist/                # output parquet files (parquet only, never csv)
    └── *.parquet
```

## Instructions

### Phase 1 — Scaffold the bundle

Bundles are initialized with `dcf::dcf_add_bundle()` (the bundle analogue of `dcf_add_source()`). This sets `process.json` `type: "bundle"` and `scripts: build.R` correctly — **never** hand-copy a source `process.json` into a bundle.

Detect R (Windows): `Rscript` is usually on PATH; otherwise look under `C:\Program Files\R\` and `%LOCALAPPDATA%\Programs\R\`. Run from the **project root**:

```r
dcf::dcf_add_bundle(
  "bundle_<name>",
  source_files = c(
    "<source_a>/standard/data.csv.gz",
    "<source_b>/standard/data_state.csv.gz"
  )
)
```

`source_files` is the list of source `standard/*.csv.gz` files this bundle reads. It is optional (you can pass `NULL` and fill it in later via the build), but passing it seeds `process.json` correctly.

### Phase 2 — Gather information

Establish, for the bundle as a whole and for **each** intended output parquet:

- **Which source folders** feed the bundle (the `data/<source>/` directory names).
- **Which specific source files** (`<source>/standard/<file>.csv.gz`) feed **each** output parquet.
- **What each parquet represents** — its grain (geography level, time resolution, demographic stratification) and its value column(s).
- Whether outputs are **wide** (one column per measure) or **tall** (a `measure`/`source`/`outcome_name` identifier column + a single `value`), and what the distinct identifier values are.

Read the candidate source files' headers so you know the real column names:

```r
vroom::vroom("../<source>/standard/<file>.csv.gz", n_max = 0, show_col_types = FALSE)
```

### Phase 3 — Write build.R

Follow the Bundle `build.R` template in `CLAUDE.md`. Rules specific to bundles:

- Read source files with relative paths from the bundle dir: `vroom::vroom("../<source>/standard/<file>.csv.gz")`. Load FIPS from `"../../resources/all_fips.csv.gz"`.
- Write **parquet only** to `dist/` (`arrow::write_parquet(df, "dist/<file>.parquet")`). Never write CSV to `dist/`.
- Keep the standard geography/time conventions (FIPS strings, `"00"` national, ISO dates).
- For tall outputs, use a single identifier column (commonly `source`, `measure`, or `outcome_name`) plus a `value` column, and derive `value_smooth` / `value_scale` variants where the visualization needs them.
- One `build.R` per bundle (integrate all outputs into it, like the single-`ingest.R` rule for sources).

### Phase 4 — Build it and generate process.json

From the project root, build the bundle. This runs `build.R`, writes the `dist/*.parquet` files, and (re)generates `process.json` — including the authoritative **`source_files`** map (which source file contributed to which parquet):

```r
dcf::dcf_process("bundle_<name>")
```

**Important:** the `source_files` block in a bundle's `process.json` is only trustworthy right after a successful `dcf_process`/`dcf_build`. It reflects the *last* build, so it goes stale if `build.R` later changes which sources it reads (e.g. after a source is renamed or split). Always (re)build **before** you read `source_files` to construct the `measure_info.json` `_bundle` map in Phase 5.

If R/dcf is unavailable, write a minimal valid bundle `process.json` by hand (`type: "bundle"`, `scripts: [{ "path": "build.R", ... }]`) and note that the `source_files` map will be filled on the next real build.

### Phase 5 — Write a fully-documented measure_info.json

Bundle `measure_info.json` uses the **bundle schema** (path-prefixed keys, `levels`, `categories`/`variants`) documented in `CLAUDE.md` — not the source schema. Read the actual parquet columns first (do not guess):

```r
names(arrow::read_parquet("dist/<file>.parquet", as_data_frame = FALSE))
```

Then satisfy **all** of the following.

#### 5a. Every column of every dist parquet must be documented

Each column must resolve to a `short_name` **and** a description. There are three column kinds:

1. **Index / standard columns** (`geography`, `time`, `date`, `year`, `age`, `sex`, `race_ethnicity`, `fips`, `payer`, `grade`, `vaccine`, `virus`, `serotype`, `survey_type`, …). These already have sensible defaults in `build_docs.R`'s `STANDARD_VARS`, so you may omit them — but **add an explicit entry whenever the bundle's meaning is more specific** than the generic default (e.g. a `geography` column that holds state *names* rather than FIPS codes, or a `payer` column).

2. **Tall-format identifier columns** (`source`, `measure`, `outcome_name`, …). Give them a `levels` block enumerating the distinct values. It is acceptable — and expected — for these to be documented **only** as their value list (rendered as "Values: …" in the docs); a per-column `short_description` is optional here. Inherit each level's metadata from the contributing source's `measure_info.json` with `"source_id": "<measure_in_source>"` when a matching measure exists; use `{}` when the level name is self-explanatory.

   ```json
   "bundle_<name>/dist/<file>.parquet|source": {
     "short_name": "Data source",
     "levels": {
       "Epic Cosmos, ED": { "source_id": "epic_pct_rsv" },
       "CDC NSSP":        { "source_id": "percent_visits_rsv" }
     }
   }
   ```

3. **Value / measure columns** (`value`, `value_smooth`, `pct_resistant`, `wapo_school_mmr_rate`, …). Give a full entry: `short_name`, `long_name`, `short_description`, `long_description` (may reuse short), `measure_type`, `unit`, `time_resolution`, and `sources`. When a value column mirrors a measure that already exists in a source's `measure_info.json`, use the shorthand `{ "source_id": "<measure_in_source>" }` to inherit its documentation instead of duplicating it.

Use `variants` when several value columns differ only by a transform (e.g. `value`, `value_smooth`, `value_scale`, `value_smooth_scale`) and `categories` to apply one template across multiple parquet files — see the `bundle_respiratory` `{category}value{variant}` entry for the canonical example. This avoids repeating a description dozens of times.

#### 5b. Record the bundle's sources and the file→parquet map (`_bundle` block)

Add a top-level `_bundle` object (a bundle-only extension; `build_docs.R` ignores unknown top-level keys, so it is safe). It records **all source folders** feeding the bundle and, for **each** dist parquet, exactly which **source files** contribute to it. Build the file→parquet map from the freshly-regenerated `process.json` `source_files` (Phase 4), inverted to be keyed by parquet:

```json
"_bundle": {
  "name": "bundle_<name>",
  "sources": ["<source_a>", "<source_b>"],
  "dist_files": {
    "<file_1>.parquet": {
      "sources": ["<source_a>"],
      "source_files": ["<source_a>/standard/data.csv.gz"]
    },
    "<file_2>.parquet": {
      "sources": ["<source_a>", "<source_b>"],
      "source_files": [
        "<source_a>/standard/data.csv.gz",
        "<source_b>/standard/data_state.csv.gz"
      ]
    }
  }
}
```

- `_bundle.sources` = the sorted unique union of every source folder in `dist_files[*].sources`.
- Every parquet in `dist/` must appear as a key in `dist_files`.
- Keep the paths exactly as `build.R` reads them (`<source>/standard/<file>.csv.gz`).

#### 5c. Optional `_sources`

Add a `_sources` block only if the bundle introduces sources or restriction wording not already documented in the contributing sources' own `measure_info.json`. Follow the `_sources` schema and special restriction wording in `CLAUDE.md` (Epic Cosmos, Google Health Trends, CDC/CMS, academic).

### Phase 6 — Validate

1. **JSON parses**: `jsonlite::fromJSON("data/bundle_<name>/measure_info.json")` without error.
2. **Full coverage**: every column of every `dist/*.parquet` either has an entry in `measure_info.json` (direct key, template, or `levels`) or is a `STANDARD_VARS` default. No value column should fall through to a bare column name.
3. **`_bundle` completeness**: every dist parquet is a key under `_bundle.dist_files`, and every listed `source_file` exists.
4. **Docs render**: run `Rscript scripts/build_docs.R` from the repo root and confirm the bundle's section on the generated `docs/index.html` shows a short name + description (or "Values: …") for every variable.
5. Consider adding the bundle to the daily flow if it is not already picked up by `dcf::dcf_build()`.

### Phase 7 — Commit

Commit `build.R`, `measure_info.json`, `process.json`, the `dist/*.parquet` files, and the regenerated `docs/` + `resources/data_manifest.json`.

## Reference: a worked example (bundle_youth_wellbeing)

Sources `medicaid_quality` + `cms_mmd`; four tall parquets each with an `outcome_name` identifier and a `value`:

```json
{
  "bundle_youth_wellbeing/dist/medicaid_youth_wellbeing.parquet|outcome_name": {
    "short_name": "Wellbeing measure",
    "levels": {
      "Adolescent Well-Care Visits": {},
      "Developmental Screening": {}
    }
  },
  "bundle_youth_wellbeing/dist/medicaid_youth_wellbeing.parquet|value": {
    "short_name": "Medicaid youth wellbeing rate",
    "long_name": "Medicaid and CHIP Youth Wellbeing Rate",
    "short_description": "Percent of Medicaid/CHIP child beneficiaries who received the service.",
    "measure_type": "Percent",
    "unit": "%",
    "time_resolution": "Year",
    "sources": [{ "id": "medicaid_quality" }]
  },
  "_bundle": {
    "name": "bundle_youth_wellbeing",
    "sources": ["cms_mmd", "medicaid_quality"],
    "dist_files": {
      "medicaid_youth_wellbeing.parquet": {
        "sources": ["medicaid_quality"],
        "source_files": ["medicaid_quality/standard/data.csv.gz"]
      },
      "cms_youth_wellbeing_state.parquet": {
        "sources": ["cms_mmd"],
        "source_files": ["cms_mmd/standard/data_state_county_age.csv.gz"]
      }
    }
  }
}
```

## Key gotchas

- **Bundle vs. source schema** differ. Bundle keys are path-prefixed (`bundle_x/dist/file.parquet|col`); source keys are bare column names. Do not mix them.
- **`dist/` is parquet-only.** No CSV in `dist/`.
- **`source_files` staleness** — regenerate `process.json` (Phase 4) before trusting it (Phase 5b).
- **Never hand-copy a source `process.json`** into a bundle — use `dcf_add_bundle` so `type`/`scripts` are correct.
- **Read real columns** from the built parquets; do not infer them from `build.R` alone.
